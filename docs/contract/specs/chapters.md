# Chapters and media segments

The chapter marks a media file carries (ffprobe chapters, the MKV/MP4 chapter atoms) and what a client sees of them: `Chapters` on the item and `GET /MediaSegments/{itemId}`. Probed on the 12.2 reference with online metadata off.

Scenarios: [`../scenarios/chapters.json`](../scenarios/chapters.json). Fixture state: [`../fixtures.json`](../fixtures.json), media from `scripts/conformance-media.sh` (lazy library `Chapters`).

## Fixture facts this spec relies on

* `Chaptered Movie (2500)` is a 6 s MKV with three chapters: `Opening` at 0 s, an untitled one at 2 s and `Finale` at 4 s.
* `Plain Chapterless (2501)` is an MP4 with no chapters.

## <a id="dto"></a>Chapters on the item

- **chapters.dto.R1** `Chapters` is a list of `{StartPositionTicks, Name, ImageDateModified}` in start order, `StartPositionTicks` being the chapter's start in 100 ns ticks (2 s is `20000000`).
- **chapters.dto.R2** A chapter's `Name` is its title tag; a chapter without one is `Chapter N` with N its 1-based position in the list (`Chapter 2`, `Chapter 10`, no zero padding).
- **chapters.dto.R3** `ImageTag` is a member only when a chapter picture exists; `ImageDateModified` is then the picture's date and otherwise `0001-01-01T00:00:00.0000000Z`. A single read (`GET /Items/{itemId}`, `GET /Users/{userId}/Items/{itemId}`) carries the list without `Fields`.
- **chapters.dto.R4** An item without chapters (any item without a media file included) has `Chapters: []` on a single read.

## <a id="images"></a>Chapter pictures

A still taken at each chapter mark, opt-in per library. Scenarios: [`../scenarios/chapters2.json`](../scenarios/chapters2.json) (lazy libraries `ChapterImg`, `ChapterImgTask` and `ChapterImgOff`; the videos are 640x360 ramps whose brightness grows with time, so the moment a still was taken at can be read off its pixels) and [`../scenarios/chapters3.json`](../scenarios/chapters3.json) (lazy libraries `ChapterImg3` and `ChapterImgToggle`; detailed, noisy videos of several sizes, so a picture made again at another quality has other bytes; a picture's size is read from its JPEG or PNG header, a re-encoded one is told from the stored one by the `Lavc` comment only the stored still carries).

- **chapters.images.R1** Pictures are made only for videos of a library with `EnableChapterImageExtraction` true (the default is off). A chapter that has one carries `ImageTag` (32 hex digits) and `ImageDateModified` (the picture's date) in `Chapters` (single read; a listing with `Fields=Chapters`); one without has neither member's value (`ImageTag` absent, the zero date, `chapters.dto.R3`).
- **chapters.images.R2** `GET /Items/{itemId}/Images/Chapter/{index}` (`Chapter` in any case, `index` 0-based into `Chapters`, 0 when it is left out) answers `200` `image/jpeg`, the still, with `Cache-Control: public`. It is public like the other picture routes (no token needed). A `tag` query value (not checked against the picture) makes the answer `Cache-Control: public, max-age=31536000, immutable` with `ETag` the tag.
- **chapters.images.R3** `404` for an index past the last chapter, a negative index, a chapter without a picture and an item that does not exist; a `400` validation problem on `imageIndex` for an index that is not an integer.
- **chapters.images.R4** A picture is taken at the chapter's start, except that a chapter starting at 0 is taken at 15 s. The pictures of an item are taken in the order of its chapters and the first one that cannot be taken (the position is past the end of the video or too close to it to hold a frame) ends the work for the item: the pictures before it are kept and the chapters from it on have none. A 10 s file with chapters at 0 s and 5 s has none (the first is the failing one), a 14 s file and a 15 s one with chapters at 0 s and 7 s have none, a 16 s one has both, and a 20 s file with chapters at 5 s and 19.95 s has the picture of the first only. An item whose extraction stopped is not tried again until its file changes.
- **chapters.images.R5** With `ExtractChapterImagesDuringLibraryScan` true the pictures are made right after the library scan; with only `EnableChapterImageExtraction` they are made by the `Extract Chapter Images` task (`RefreshChapterImages`, id `4e6637c832ed644d1af3370a2506e80a`, category `Library`, daily at 02:00), which skips libraries that have extraction off. A refresh of the item does not make them. A scan of unchanged media does not make them again.
- **chapters.images.R6** The picture route reshapes the still when asked, with these query members (names in any case, the first of a repeated name counts, a space before a number is ignored, an empty value is a missing one): `width` and `height` set the size (both: exactly that size, the aspect ratio is dropped; one: the other side follows the ratio), then `maxHeight` and `maxWidth` cap it, in that order, each on the size the step before gave (a `0` or negative value is no cap; a side above its cap becomes the cap and the other side follows the ratio of the size at that moment: for a 650x366 picture `maxWidth` 200 with `maxHeight` 64 is 114x64; for 640x360 `maxWidth` 111 with `maxHeight` 111 is 111x63, `maxWidth` 72 with `maxHeight` 71 is 72x41), then `fillWidth` and `fillHeight` make it cover that width and height. "The other side follows" is `(new side / old side) * other side`, in that order, rounded to the nearest integer with a tie going to the even one (of 640x360 `width` 24 is 24x14, `width` 56 is 56x31, `width` 40 is 40x22). Fill works with a divisor: the smaller of the current width over `fillWidth` and the current height over `fillHeight` (a missing or `0` one is left out); when it is above 1 each side is divided by it and rounded up (`fillWidth` 61 of 640x360 is 62x35, `fillWidth` 624 is 624x352 and 245 is 246x138: the arithmetic is floating point and the quotient is not cleaned); when the shorter side comes out as 1 the longer one is the ratio of the current sides rounded up whatever was asked (`fillWidth` 1 is 2x1, `fillHeight` 1 of 360x640 is 1x2, `width` 327 with `height` 29 and `fillWidth` 5 is 12x1). A negative `fillWidth` or `fillHeight` cancels the fill; a `0` is a missing one. Fill is not an enlargement and only acts when the picture is made again for another reason (R8). A side that comes out as 0 before the clamp of R7 (`width` 640, `height` 54, `maxWidth` 5) leaves the picture as it is, the stored JPEG, whatever `format` is asked. Of a 640x360 picture `maxWidth` 100 is 100x56, `maxHeight` 40 is 71x40, `width` 100 with `height` 50 is 100x50, `maxWidth` 100 with `maxHeight` 30 is 53x30 and `fillWidth` 100 (with `quality` 50) is 100x57.
- **chapters.images.R7** A picture is never enlarged: a size above the picture's own (a `width` or `height` larger than it, a pair larger than it on either side) is brought back inside the picture's size keeping the shape that was asked for, a side never below 1 (`width` 200 with `height` 200 of a 120x68 picture is 68x68, `width` 2000 is 120x68, `fillWidth` and `fillHeight` above the size change nothing). The steps of R6 run on the unclamped numbers and the result is clamped last (`height` 111 with `maxWidth` 40 of that picture is 40x23).
- **chapters.images.R8** The stored still is served as it is, byte for byte, unless the request changes it. It is made again (JPEG, quality 100 unless `quality` says otherwise) when `maxWidth` or `maxHeight` is below the picture's side or is 0 or negative, when `width` or `height` differs from its side, when `quality` is below 90 (a value below 1 is 1, above 100 is 100), or when `format` is a known format other than `jpg` and `svg`. `maxWidth`, `maxHeight`, `width` or `height` equal to or above the side, `quality` 90 to 100 and above, `format` `jpg`, an unknown word, a number 2 and an empty value, and `fillWidth`, `fillHeight`, `tag` alone, leave it as it is. `svg` (or 5) leaves it as it is whatever else is asked.
- **chapters.images.R9** `format` is a name in any case or its number: `Bmp` 0, `Gif` 1, `Jpg` 2, `Png` 3, `Webp` 4, `Svg` 5. `Png` answers `image/png`, a PNG of the size R6 gives (the quality does not apply); `Bmp` and `Gif` answer a JPEG made again; `Webp` answers `image/webp` (R16). A word that is not a name is ignored; a number out of 0 to 5 is `400` `text/plain` `Error processing request.`.
- **chapters.images.R10** A `tag` query value (or the tag of the long form, R12) sets `ETag` to `"<tag>"` and `Cache-Control` to `public, max-age=31536000, immutable`; without it (or empty) there is no `ETag` and the cache control is `public`. The answer carries `Last-Modified` and honors `If-None-Match` (against that `ETag`) and `If-Modified-Since` with `304`, for the stored still and for a reshaped one. `Range` is ignored (the whole picture, `200`), `HEAD` answers like `GET` without a body. The route needs no token.
- **chapters.images.R11** A value that cannot be read as a number is `400` with a validation problem naming every bad member (`maxWidth`, `maxHeight`, `width`, `height`, `fillWidth`, `fillHeight`, `quality`, `blur` and `unplayedCount` are 32-bit integers, `percentPlayed` a decimal number, `imageIndex` an integer): `maxWidth=abc&quality=x` names both, `maxWidth=abc` with an index `x` names `maxWidth` and `imageIndex`; `2147483648` is not a number. `addPlayedIndicator`, `cropWhitespace`, `backgroundColor`, `foregroundLayer` and members nobody reads are not validated. A missing picture is `404` whatever else is asked.
- **chapters.images.R12** The long form `GET /Items/{itemId}/Images/Chapter/{imageIndex}/{tag}/{format}/{maxWidth}/{maxHeight}/{percentPlayed}/{unplayedCount}` is the same route with those members in the path; they win over the query, the other members are read from the query. A `format` that is not a name or a number of R9 is a `400` naming `format` (here, unlike the query), a `0` size is "given" for R8 (so `Jpg/0/0/0/0` is made again). Fewer path members than the six is not a route (`404`).
- **chapters.images.R13** The options are read when the pictures are made, not when they are saved: saving `EnableChapterImageExtraction` on a library whose scan has passed makes none until the next library scan (with `ExtractChapterImagesDuringLibraryScan` set) or the task, and that scan makes them although the media did not change. A scan after that makes them again no more than the first one did, switching extraction off keeps the pictures that exist, and a refresh of the item (`ReplaceAllImages` included) neither makes, replaces nor removes them. A changed file (size or date) gets its pictures made again.
- **chapters.images.R14** The reference puts the server path of the picture in `ImagePath` of every `Chapters` entry that has one, for every caller and every way to read the item (single read, user route, listing with `Fields=Chapters`). Tinyfin never does (divergence, `chapters.images.path`).

- **chapters.images.R15** The overlay members make the picture be made again when they mean something, and are drawn on it at its final size, in this order: `blur`, `foregroundLayer`, the played bar, the unplayed count. `blur` (any whole number, `0` and negative ones included, the first of a repeated name; an empty value is a missing one) makes it again; a positive one is a gaussian blur of that sigma (what lies outside the picture counts as black, so the borders go dark). `percentPlayed` makes it again unless it is `0`, `100`, negative or above 100 (`NaN` does, and draws nothing); a value from 0 to 100 draws, on the last 9 rows, a 60 % black backdrop from the left edge to the last column but one and over it, from the left, a solid `#00A4DC` bar `round((width - 1) * percent / 100)` pixels wide. `unplayedCount` of 1 or more draws a `#00A4DC` circle (80 % opaque, radius 20) centred 38 pixels from the top and 38 from the right edge, with the number in white; 0 and negative are nothing. `backgroundColor` makes it again when it is 6 or 8 hex digits (a `#` first is allowed) and changes no pixel (the picture has no transparency); any other value is nothing. `foregroundLayer` makes it again whenever it is not empty and puts a black layer over the picture: a whole number is the layer's alpha (its low byte; a multiple of 256, `0` included, makes the picture black: `80` turns a value `v` into `v * 175 / 255`), anything that is not a whole number is a layer of alpha 153 (60 %, as `zzz`, `ff` or `0x10`), `1.5` is one of alpha 128. `addPlayedIndicator` and `cropWhitespace` alone change nothing (the stored still is served as it is) and nothing with them either. The overlays work on a picture that keeps its size (a request with only an overlay is the stored size, JPEG at quality 100).
- **chapters.images.R16** `format=Webp` (or `4`) answers `image/webp`, a lossless WebP (a `VP8L` stream) at the default quality, `Content-Type` `image/webp`; the reference makes a lossy `VP8 ` one below quality 100 (Tinyfin keeps the lossless one). A caller whose `Accept` lists `image/webp` as a media type of its own (parameters, `q` included, are not looked at; case-sensitive: `IMAGE/WEBP` and `image/webpx` do not count) gets WebP once the picture is made again for another reason (R8) and no format was asked for: a format name or number that is not `Jpg`/`Bmp`/`Gif`/`Png`/`Svg`, an unknown word and an empty value leave the choice to `Accept`; `Jpg` (2), `Bmp` (0), `Gif` (1) and `Png` keep what they say. `Accept` alone never makes the picture again. Every picture answer carries `Vary: Accept`. A picture whose side comes out as 0 (R6) is the stored JPEG whatever the format.

## <a id="fields"></a>Listings

- **chapters.fields.R1** A listing (`GET /Items`) carries `Chapters` only when `Fields` contains `Chapters` (empty list for an item without chapters); without it the member is absent.
- **chapters.fields.R2** `Fields` names are case-insensitive.

## <a id="segments"></a>Media segments

- **chapters.segments.R1** `GET /MediaSegments/{itemId}` answers `{Items, TotalRecordCount, StartIndex}`. With no segment provider configured the list is empty (`TotalRecordCount` 0, `StartIndex` 0); chapters are not turned into segments.
- **chapters.segments.R2** `includeSegmentTypes` (repeatable, or comma separated) takes the segment type names `Unknown`, `Commercial`, `Preview`, `Recap`, `Outro`, `Intro` in any case, or their numbers 0 to 5, and only filters.
- **chapters.segments.R3** An unknown type name, an empty value or a number outside 0 to 5 is a `400` validation problem on `includeSegmentTypes` (checked before the item is looked up). A comma list is invalid as a whole when any entry is.
- **chapters.segments.R4** An unknown well-formed id is `404`, a malformed one `400`, an anonymous caller `401`.

## Known differences

* **Chapter pictures.** Tinyfin writes each still, at the video's own size, to `<data dir>/chapters/<item id>/<start ticks>.jpg` (with a `.stamp` of the video's size and date; a changed file is extracted again, a stopped extraction leaves a `.partial` marker) and answers a reshaped one from a copy kept beside it (`cache/`, removed with the stills). `ImageTag` is a digest of the file's path and date, so it differs by value. The reference also puts the picture's server path in `ImagePath` of every `Chapters` entry, for every caller; Tinyfin never does (a path leak, security-driven divergence, `chapters.images.path`). Extraction is one ffmpeg at a time and concurrent with the scan's tail, so a scenario waits for the tags (retries).
* **Reshaped pictures.** Sizes follow R6 to R8 and are asserted from the picture headers. Overlays (R15) match the reference to a pixel or two on flat pictures (bar, backdrop, circle, foreground layer, small blurs); the digits of the unplayed count are drawn with a small built-in 3x5 pixel font, not the reference's typeface, a blur with a sigma of about 40 or more differs (the reference's blur is cheaper for large sigmas), `cropWhitespace` does nothing. WebP (R16) is always lossless (the Go build has no VP8 encoder; the reference's lossy output below quality 100 is not reproduced); the pixels and byte sizes differ (the reference's resampler and encoder are not Tinyfin's); 
* **Disc images and `.strm`.** Chapters are read from the file ffprobe probes at scan time. A `.strm` item (probed on play) has none.
* **Existing databases.** Migration 0026 drops the scan signatures so every item is probed again once, to pick its chapters up.
