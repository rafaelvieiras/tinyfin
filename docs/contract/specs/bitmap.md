# Picture subtitles (PGS, DVD, DVB)

The subtitle tracks that are pictures, not text: how a media file's PGS (Blu-ray), DVD and DVB tracks appear in the streams of an item, how they are offered to a player (burned into the video, kept in the container, or as a file), the route that serves them as files, and the burn-in itself. Probed on the 12.2 reference with online metadata off. Text tracks are in [`subtitles.md`](subtitles.md).

Scenarios: [`../scenarios/bitmap.json`](../scenarios/bitmap.json). Fixture state: [`../fixtures.json`](../fixtures.json), media from `scripts/conformance-media.sh` (lazy library `Bitmap`; the PGS stream is written by `scripts/conformance-pgs.py` because ffmpeg has no PGS encoder, the DVD and DVB tracks are ffmpeg re-encodes of it). Rule IDs are stable (`bitmap.<topic>.R<n>`).

## Fixture facts this spec relies on

* All four are 4 s MKV files, 320x240, with an AAC track (index 1) and picture cues showing the words BURN IN as white block letters at the bottom, from 0.5 s to 3.5 s.
* `Bmp Pgs (2650)`: one PGS track "eng" at index 2. `Bmp Dvd (2651)`: one DVD track "eng". `Bmp Dvb (2652)`: one DVB track "eng" (a cue with no end time). All three are flagged default.
* `Bmp Mixed (2653)`: SubRip "eng" (2, default), PGS "por" (3), DVD "spa" (4); only the first is flagged default.

## <a id="streams"></a>The streams of an item

- **bitmap.streams.R1** A picture track is a `Subtitle` stream with `Codec` `PGSSUB` (Blu-ray PGS), `DVDSUB` or `DVBSUB`, `IsTextSubtitleStream` false and `IsExternal` false; `IsDefault`/`IsForced`/`Language` come from the container, and `DisplayTitle` is `<Language> [- Default] [- Forced] - <CODEC>` (`English - Default - PGSSUB`, `Portuguese - PGSSUB`).
- **bitmap.streams.R2** A PGS or DVD track has `SupportsExternalStream` true and the `Width`/`Height` of the picture it draws on (the file's own subtitle size, here 320 and 240). `Score` is present only for a track that is default or forced (`subtitles.discover.R10`): a default picture track scores 112211, the default text track beside it 112221; a picture track that is neither default nor forced has none.
- **bitmap.streams.R3** A DVB track has `SupportsExternalStream` false, no `Width`/`Height`, and a score one hundred lower than the same track in another codec (a default DVB track is 112111).

## <a id="delivery"></a>How PlaybackInfo offers them

- **bitmap.delivery.R1** A picture track is never converted to text: an `Hls` or `External` entry for a text format (`vtt`, `srt`, ...) does not take it, so it is `Encode` (burned into the video) while the text track beside it keeps its method. It has no `DeliveryUrl`.
- **bitmap.delivery.R2** When the selected track (`SubtitleStreamIndex`) is delivered by `Encode`, the source is transcoded: `SupportsDirectPlay` false and `TranscodingUrl` carrying `SubtitleMethod=Encode`, the `SubtitleStreamIndex` and `TranscodeReasons=SubtitleCodecNotSupported`.
- **bitmap.delivery.R3** An `Embed` entry whose `Format` is the track's codec name (`pgssub`, `dvdsub`, `dvbsub`, in any case) keeps the track in the container: the track is `Embed`, and when it is the selected one the source can still be direct played. A track whose codec no entry names is `Encode`.
- **bitmap.delivery.R4** When the selected track is not `Embed`, nothing is embedded (`subtitles.delivery.R4`): every track is `Encode` and the source is transcoded. A container that cannot hold the track (the profile's direct play container does not match the file) transcodes and burns it as well.
- **bitmap.delivery.R5** An `External` entry whose `Format` is the track's codec name (case-insensitive, `pgssub` for PGS, `dvdsub` for DVD, `dvbsub` for DVB) delivers the track as a file: `External`, `DeliveryUrl` `/Videos/{item id, dashed}/{media source id}/Subtitles/{index}/0/Stream.{format}?ApiKey={token}` with the format spelled as the entry spells it (`.PGSSUB`), `IsExternalUrl` false.
- **bitmap.delivery.R6** Other names do not match: `sup`, `pgs`, `hdmv_pgs_subtitle`, `vobsub` for a PGS or DVD track are `Encode`. A DVB track is delivered `External` by an entry named `dvbsub` although the route does not serve it (`bitmap.route.R3`).

## <a id="route"></a>The track as a file

- **bitmap.route.R1** `GET /Videos/{itemId}/{mediaSourceId}/Subtitles/{index}/Stream.{format}` for a PGS track answers `200` `application/octet-stream`, the track as a `.sup` stream (it starts with `PG`); for a DVD track `200` `video/x-matroska`, a Matroska file that holds only that track. A `.sup` sidecar file is served as it is. Start position, end position and `copyTimestamps` are accepted and ignored.
- **bitmap.route.R2** The formats that name a picture track are `pgssub`, `sup`, `pgs`, `hdmv_pgs_subtitle`, `dvdsub` and `vobsub` (any case), all meaning "the track as stored"; for a DVD track the container extension `mks` is one as well. Anything else (`srt`, `vtt`, `ass`, `dvbsub` on a PGS or DVD track, `dvd_subtitle`, `mks` on a PGS track, unknown names) is a `400`: picture tracks are not converted.
- **bitmap.route.R3** A DVB track has no file: `404` for every format.

## <a id="hls"></a>HLS

- **bitmap.hls.R1** A picture track is never listed in the master playlist's `#EXT-X-MEDIA:TYPE=SUBTITLES` group (`playback.hls.R7`): with the text track selected and `Hls` delivery the group has that one track and no `Subtitles/3/`, `Subtitles/4/` URI.
- **bitmap.hls.R2** With a picture track selected the master has no subtitle group at all and its variants carry `SubtitleMethod=Encode`: the picture is in the video.

## <a id="burnin"></a>The burn-in

- **bitmap.burnin.R1** [untestable: a property of the picture's pixels; covered by a Go test with a real ffmpeg] A burned-in picture track is decoded to frames and overlaid on the video at the position its cues give (the cue canvas is the picture's size), shown from the cue's start and removed at its end; a track whose cues carry no end (DVD and DVB from the fixtures) stays on screen. Both servers use ffmpeg's `overlay` filter (R3). Not asserted by a scenario (it is a property of the pixels): `go test ./internal/transcode -run BitmapBurnIn` builds a PGS and a DVD track, transcodes with `Subtitle.Bitmap`, and checks by pixel difference against the plain transcode that nothing differs before the cue, the cue's pixels are there inside its window and (PGS) gone after it. The same frames were checked on both servers through `master.m3u8` / `main.m3u8` of a real transcode (cue from 0.5 s to 3.5 s: the difference with the plain transcode starts at the first sample inside the window, PGS ends with it, DVD/DVB persist).

- **bitmap.burnin.R2** [untestable: the arguments of ffmpeg] A picture burn-in passes `-canvas_size <W>x<H>`, the size of the subtitle stream (a DVB track has none: no option), before every input: the video and, for a sidecar (`.idx`, `.sup`, `.mks`), the sidecar file as a second input. The pictures are read from that input's first subtitle stream (`-map` of the sidecar's stream). Tinyfin probes the files for these sizes when it starts the job.
- **bitmap.burnin.R3** [untestable: the arguments of ffmpeg] The filter graph is `[<in>:<stream>]scale,scale=<W>:<H>:fast_bilinear[sub];[0:0]setparams=color_primaries=bt709:color_trc=bt709:colorspace=bt709[,<scale of the output>],format=yuv420p[main];[main][sub]overlay=eof_action=pass:repeatlast=0`, with `<W>x<H>` the size of the output picture. When the track's size has another shape than the output (or is unknown) the pictures are fitted to the height instead: `scale,scale=-1:<H>:fast_bilinear,crop,pad=max(<W>\,iw):max(<H>\,ih):(ow-iw)/2:(oh-ih)/2:black@0,crop=<W>:<H>`; the same shape in another size (640x480 on a 320x240 picture) is a plain scale. Checked by pixel difference on both servers for PGS, DVD, DVB, an index file, a canvas wider and one narrower than the picture.
- **bitmap.burnin.R4** [partly testable: the scenarios check that every case transcodes; the arguments are untestable] A text burn-in is `setparams=...bt709[,<scale>],format=yuv420p,subtitles=f='<file>'[:charenc=<enc>]:fontsdir='<dir>'`: the colour tags, the scale and the pixel format come first and the text is rendered on the picture the viewer gets. An embedded track is extracted first (an ASS or SSA track as ASS, any other as SubRip) and the file burned; in an ASS file the style font `Arial` is replaced by `Arial Unicode MS`, as when the track is served (`subtitles.stream.R6`).
- **bitmap.burnin.R5** [partly testable: the scenarios check that every case transcodes; the arguments are untestable] An external text file whose stream has a language gets `charenc=<encoding>` from its content, by a statistical detector: `ascii` (no byte above 0x7F), `utf-8` (a byte order mark, or valid UTF-8 with at least three multi-byte characters; fewer read as `windows-1250`), `utf-32le`/`utf-32be` for a UTF-32 byte order mark, `shift-jis`, `euc-jp`, `euc-kr`, `gb18030`, `big5`, the single-byte Cyrillic (`windows-1251`, `koi8-r`, `iso-8859-5`, `ibm866`), Greek (`iso-8859-7`), Hebrew (`windows-1255`), Arabic (`windows-1256`) and Thai (`tis-620`) pages and the Latin ones (`iso-8859-1`, `iso-8859-2`, `iso-8859-9`, `windows-1250`, `windows-1252`); a file with a UTF-16 byte order mark gets none; a file with no language none at all. The detector itself is specified exactly in the section *Charset detection* below (`bitmap.charset.R1`-`R20`); the observed answers of the reference for 84 samples are the corpus of `internal/transcode/testdata/charset-corpus.json`, checked by `TestDetectCharsetCorpus`.
- **bitmap.burnin.R6** [untestable: the arguments of ffmpeg] When the input file carries attachments (the fonts of a Matroska file), they are written to a directory and the text burn-in passes it as `fontsdir`; a font a style names that is neither attached nor installed falls back to the host's fontconfig default (`subtitles3.burn.fonts` checks that every case transcodes, a font's glyphs are a property of the pixels). The same input without attachments has no attached fonts to offer.
- **bitmap.burnin.R7** [untestable: the arguments of ffmpeg] An external picture subtitle (a PGS `.sup`, a VobSub `.idx`/`.sub` pair, a Matroska file with pictures) selected for burn-in is read as a second input exactly like R2/R3, from the start of the video and from a seek position alike (`subtitles3.burn.bitmap-sidecar` requests the first and a later segment of each).
- **bitmap.burnin.R8** [partly testable: the scenario checks that the text is drawn; the glyphs are pixels] The fallback faces of a burned-in text are the reference image's: a style font that is neither attached nor installed is drawn in DejaVu Sans (fontconfig's `sans-serif`), CJK text in WenQuanYi Zen Hei, so the picture of a missing font is the same on both servers (checked by decoding the frames of both for Latin, CJK, Cyrillic and Greek text: identical). Tinyfin's image ships those two fonts and a `fonts.conf` (`deploy/fonts.conf`), because libass draws no text at all when fontconfig has no configuration (`Failed to load fontconfig fonts!`), whatever `fontsdir` says; a host without a fontconfig configuration gets a generated minimal one (fonts directories of the job, the configured one, the first system font directory found) through `FONTCONFIG_FILE` for the ffmpeg process. (`subtitles4.burn.fonts-cjk`; Go test `TestFontEnv_WritesConfigWithoutFontconfig`)

## Known differences

* **Fonts.** The faces match when the same fonts are installed (R8): Tinyfin's image ships DejaVu Sans and WenQuanYi Zen Hei like the reference's. A Tinyfin run on a host without them draws the host's fallback faces; positions and sizes are identical, glyph shapes can differ. Attached fonts are used by both (R6).
* **Charset detection.** None left on the recorded samples: Tinyfin implements `bitmap.charset.R1`-`R20` (`internal/transcode/charset*.go`, tables in `internal/transcode/chardata/`, kept equal to `docs/contract/data/`) and reproduces all 84 answers of the corpus, the short and ambiguous samples included. A file in a code page that no table has gets whatever the statistical tables give (usually `windows-1252` or a Latin-2 name), not a fixed `iso-8859-1`.
* **Seeking.** None left in what the picture and sound of a burn-in carry: segments of a text and of a picture burn-in at a seek position, near the end of the file and past it are byte-identical to the reference's on the fixtures tried (the arguments differ: the reference seeks with `-ss` and `-copyts`, Tinyfin shifts the timestamps around the renderer). The reference's `-sn -map -0:0` on a picture burn-in only keeps the original picture and subtitle streams out of the output, which Tinyfin's `[v]` label does already.
* **Existing databases.** Picture tracks gain `Width`/`Height` when the file is probed again; an item scanned before only gets them with its next probe.

## Charset detection (bitmap.charset)

This section defines, exactly, the detector behind `bitmap.burnin.R5` (the `charenc` of a text burn-in) and behind the decoding of external text subtitles that are served as text. It reproduces the reference's statistical detector (a Mozilla-universal-charset-detector derivative: byte-order-mark check, coding state machines, character-frequency probers for the CJK encodings, language sequence models for the single-byte code pages and a Latin-1 fallback prober). The answer is a function of the file's bytes only; the same bytes always give the same name. The 84 recorded samples (`internal/transcode/testdata/charset-corpus.json`) are the regression check; all 84 are reproduced by these rules (hand-checked cases in R20).

Data the rules refer to (facts about languages and encodings, not code) lives next to the specs:

- `docs/contract/data/charset-statemachines.json`: the coding state machines (R7), keyed by the encoding name each one detects.
- `docs/contract/data/charset-cjk.json`: the CJK character-frequency sets and the hiragana pair table (R10, R11).
- `docs/contract/data/charset-sbcs.json`: the single-byte language sequence tables and the per-code-page character-order maps, in prober order (R13, R14).

Conventions: all confidence values are IEEE-754 single-precision numbers and every arithmetic step is rounded to single precision in the order written (ties between candidates and the thresholds depend on it). "Byte" values are 0..255. "Chunk" means a block of at most 1024 bytes of the file, read in file order.

- **bitmap.charset.R1** [untestable: internal algorithm, checked by Go test `TestDetectCharsetCorpus`] The whole file is fed to the detector in consecutive chunks of 1024 bytes (the last one shorter), stopping early as soon as a prober reports "found" (R4) or the byte-order-mark check answers (R2). An empty file gives no answer. The detector's answer is a name (R5) or nothing; nothing and the names below that the caller maps to nothing (R6) mean "no `charenc` option". All the rules below act on the chunk as a unit: probers keep their state between chunks, but a prober never sees a chunk that came before it was created (R3).
- **bitmap.charset.R2** [untestable: internal algorithm] Byte-order mark: only the first chunk is looked at, and only when it holds at least 2 bytes. In this order: `FE FF` is `utf-16be`, except that `FE FF 00 00` is the unusual UCS-4 order named `X-ISO-10646-UCS-4-3412`; `FF FE` is `utf-16le`, except that `FF FE 00 00` is `utf-32le`; with at least 3 bytes, `EF BB BF` is `utf-8`; with at least 4 bytes, `00 00 FE FF` is `utf-32be`, `00 00 FF FE` is `X-ISO-10646-UCS-4-2143`, `2B 2F 76` followed by one of `38 39 2B 2F` is `utf-7`, `84 31 95 33` is `gb18030`. A match ends the detection with that name (nothing else is looked at). No match: the first chunk goes on to R3.
- **bitmap.charset.R3** [untestable: internal algorithm] Input state. The detector tracks one of three states, starting as "plain": a byte with the high bit set that is not `A0` makes the state "high" for good (a lone `A0` byte, the no-break space of Latin-1, does not count as a high byte at all). While the state is still "plain", a byte `1B`, or a `{` (`7B`) immediately after a `~` (`7E`) (the previous non-high byte, `A0` counting as a non-high byte for this memory, and the memory crossing chunk boundaries) makes the state "escape". The state is updated byte by byte through each chunk, before the probers see that chunk. The first time the state becomes "high" the three probers of R4 are created (in "high" state any escape-state prober is dropped); a prober created in the middle of a chunk is still given the whole chunk, and it never sees earlier chunks. In the "escape" state the escape prober of R17 is created and given this chunk and every later one.
- **bitmap.charset.R4** [untestable: internal algorithm] Probers in the "high" state. For each chunk, in this order: the multi-byte group (R9), the single-byte group (R13), the Latin-1 prober (R16). Each receives the raw chunk (each filters it itself). If one reports "found" the detection ends at once and the answer is that prober's name (for a group: the name of the member that reported, R9/R13). Nothing reads the rest of the file. A chunk in the "plain" state (no prober exists yet) is not examined further.
- **bitmap.charset.R5** [untestable: internal algorithm] End of the file without a "found". If the final state is "plain" or "escape", the answer is `ascii`. If it is "high", each of the three probers of R4 yields a (name, confidence) pair (the name is asked before the confidence; group names follow R9/R13). Pairs with confidence greater than 0.20 are kept and sorted by confidence, highest first, stably (equal confidences keep the order multi-byte group, single-byte group, Latin-1). The first pair's name is the answer; with no pair left the answer is nothing. The answer is also nothing when all three are at or below 0.20 (for instance a Latin-1 prober at 0.0 and no other candidate). A short file with a few accented letters is usually decided between the single-byte group and the Latin-1 prober (at most 0.5) on a margin of a few hundredths: see R19 and R20.
- **bitmap.charset.R6** [untestable: the arguments of ffmpeg; `subtitles3.burn.charenc` only checks that the transcode works, the mapping by Go test `TestDetectCharsetCorpus`] The answer is passed on unchanged as the encoding name, with two post-processing steps: `utf-16le` and `utf-16be` become "no option" for text files named `.ass`, `.ssa` or `.srt` (the filter converts them itself; for any other extension the name would be passed), and no answer is "no option". For decoding served text subtitles the caller treats nothing, `utf-8`, `ascii` and `us-ascii` as already UTF-8 and otherwise decodes with the named encoding; `cp949` is decoded as `ks_c_5601-1987` and `iso-2022-cn` as `x-cp50227`. All names come from the fixed set: the BOM names of R2, `utf-8`, `ascii`, the names in the tables of R7/R13 (`shift-jis`, `euc-jp`, `euc-kr`, `cp949`, `gb18030`, `big5`, `euc-tw`, `iso-2022-jp`/`-kr`/`-cn`, `hz-gb-2312`), `windows-1252` (Latin-1 prober) and the code-page names of `charset-sbcs.json`, plus `windows-1255` / `iso-8859-8` from R15.
- **bitmap.charset.R7** [untestable: internal algorithm] Coding state machines. A machine is `{classFactor, cls[256], states[], charLen[]}` (`charset-statemachines.json`). State 0 is "start", 1 is "error" and 2 is "its me"; the others are intermediate. Feeding a byte `b`: let `c = cls[b]`; if the current state is 0, remember `charLen[c]` as the length of the character being read; the new state is `states[state * classFactor + c]`. A machine starts in state 0 when its prober is created and keeps its state across chunks; it is not reset on an error. A prober that gets "error" from its machine reports "not me" and stops reading the rest of that buffer; one that gets "its me" reports "found" and stops.
- **bitmap.charset.R8** [untestable: internal algorithm] UTF-8 prober (machine `utf-8`). Counts the multi-byte characters: each time the machine returns to state 0 and the character just finished had a remembered length of 2 or more, the count rises by one. Error: "not me" (a single invalid sequence anywhere in the data excludes UTF-8 for the rest of the detection). After each buffer, if still detecting and the confidence is above 0.95, report "found". Confidence: with fewer than 6 multi-byte characters, `1 - 0.99 * 0.5^n` (n = count; n = 0 gives 0.01, 1 gives 0.505, 2 gives 0.7525, 3 gives 0.87625, 4 gives 0.938125, 5 gives 0.9690625), otherwise 0.99. Since the shortcut needs more than 0.95, 5 multi-byte characters (0.9690625) already make "found"; with 1 to 4 the prober stays a candidate at the confidences above and competes on the numbers of R5 (a single multi-byte character, 0.505, loses to any single-byte member above it, as in sample `u8-1`, which answers `windows-1250`).
- **bitmap.charset.R9** [untestable: internal algorithm] Multi-byte group. Eight members in this order: `utf-8` (R8), `shift-jis`, `euc-jp` (R12), `gb18030`, `euc-kr`, `cp949`, `big5`, `euc-tw` (R12). All are active at the start. A chunk is first filtered: every byte with the high bit set is kept, and an ASCII byte is kept only when it directly follows a high byte (or is the very first byte of the chunk); all other ASCII bytes are dropped. The filtered buffer (never empty for a non-empty chunk) is given to each active member in order. A member reporting "found" ends the group with state "found" and best member = that one. A member reporting "not me" becomes inactive; when none is active the group state is "not me". Group confidence: 0.99 when "found", 0.01 when "not me", otherwise the highest member confidence among the active ones (members are compared in order and only a strictly greater value replaces the best; starting from 0.0, so members at exactly 0.0 never become best); the group's name is the best member's name, and when there is no best yet it is computed first from the confidences, defaulting to the first member (`utf-8`).
- **bitmap.charset.R10** [untestable: internal algorithm] Character-distribution analysis, for `shift-jis`, `euc-jp`, `gb18030`, `euc-kr`, `cp949`, `big5`, `euc-tw`. For every completed two-byte character the analyzer computes an order from its two bytes `(b0, b1)` (formulas below). A negative order is ignored. Otherwise the total count rises by one, and the frequent count too when the order is below the table length and is in the frequent set of that encoding's table (`charset-cjk.json`, `distribution[...].frequentOrders`; a table is the language's character-frequency ranking, "frequent" meaning rank below 512; `tableLength` is the number of ranked characters). Orders: Shift-JIS: if `b0` is in 81..9F then `188*(b0-0x81)`, if in E0..EF then `188*(b0-0xE0+31)`, otherwise negative; add `b1-0x40`, and subtract one more if `b1 > 0x7F`. EUC-JP: `94*(b0-0xA1) + b1-0xA1` when `b0 >= A0`, else negative. Both use the table `sjis_eucjp`. GB18030: `94*(b0-0xB0) + b1-0xA1` when `b0 >= B0` and `b1 >= A1` (table `gb2312`). EUC-KR and CP949: `94*(b0-0xB0)+b1-0xA1` when `b0 >= B0` (table `euckr`). Big5: when `b0 >= A4`: `157*(b0-0xA4) + (b1-0xA1+63)` if `b1 >= A1`, else `157*(b0-0xA4) + (b1-0x40)`; otherwise negative (table `big5`). EUC-TW: `94*(b0-0xC4)+b1-0xA1` when `b0 >= C4` (table `euctw`). Confidence: if the total is 0 or the frequent count is 4 or less: 0.01. If total differs from frequent: `r = frequent / ((total - frequent) * ratio)` and when `r < 0.99` that is the confidence. Otherwise 0.99. `ratio` is the table's `typicalDistributionRatio` (Japanese 3.0, Big5 0.75, EUC-TW 0.75, GB 0.9, Korean 6.0). "Enough data" means a total above 1024.
- **bitmap.charset.R11** [untestable: internal algorithm] Japanese pair analysis (`shift-jis` and `euc-jp` only). Every character the probers finish (one-byte characters included) updates a chain: its hiragana order is computed (Shift-JIS: `b0 = 0x82` and `b1` in 9F..F1 gives `b1-0x9F`; EUC-JP: `b0 = A4` and `b1` in A1..F3 gives `b1-0xA1`; only for two-byte characters; everything else is "none"). If both the previous and the current character have an order, the pair count rises by one and the cell `jpContext[previous][current]` (`charset-cjk.json`, categories 0..5) is counted in its category; then the current becomes the previous (a "none" breaks the chain). Counting stops (and the previous characters no longer matter) once the pair count has exceeded 1000, which is checked at the start of the next character. Confidence: with more than 4 pairs, `(pairs - category0) / pairs`; otherwise -1 ("don't know"). "Enough data" means more than 100 pairs.
- **bitmap.charset.R12** [untestable: internal algorithm] Multi-byte members other than UTF-8. Each owns a machine named like it (R7) and the analysis of R10 (plus R11 for Japanese). Reading a buffer byte by byte: the machine's "error"/"its me" answers end the member as in R7. When the machine returns to state 0 after byte `i`, a character of the remembered length just ended; the analyzers are fed the two bytes `(buf[i-1], buf[i])` (when `i = 0` the first byte is the last byte of the previous filtered buffer, 0 before the first buffer), only when the remembered length of that character is 2. After the buffer the last byte is remembered. Afterwards, if still detecting and "enough data" holds (for `shift-jis`/`euc-jp` the pair condition of R11, for the others a total above 1024) and the confidence is above 0.95, the member reports "found". Confidence: the highest of the distribution confidence and, for `shift-jis`/`euc-jp`, the pair confidence; for the others the distribution confidence. `cp949` uses its own machine and the Korean table. Names: `shift-jis`, `euc-jp`, `gb18030`, `euc-kr`, `cp949`, `big5`, `euc-tw`.
- **bitmap.charset.R13** [untestable: internal algorithm] Single-byte group: 101 members in the order of `charset-sbcs.json` (`probers`): 0 Russian windows-1251, 1 koi8-r, 2 iso-8859-5, 3 x-mac-cyrillic, 4 ibm866, 5 ibm855; 6 Greek iso-8859-7, 7 windows-1253; 8 Bulgarian iso-8859-5, 9 windows-1251; 10 the Hebrew helper (R15), 11 Hebrew windows-1255 (logical), 12 Hebrew windows-1255 (visual, same table read backwards); 13 Thai tis-620, 14 iso-8859-11; 15-17 French (iso-8859-1, iso-8859-15, windows-1252); 18-20 Spanish (same three); 21 Hungarian iso-8859-2, 22 windows-1250; 23-25 German (ibm850, iso-8859-1, windows-1252); 26 Esperanto iso-8859-3; 27-28 Turkish (iso-8859-3, iso-8859-9); 29-30 Arabic (iso-8859-6, windows-1256); 31-32 Vietnamese (viscii, windows-1258); 33-35 Danish (iso-8859-15, iso-8859-1, windows-1252); 36-38 Lithuanian (iso-8859-13, iso-8859-10, iso-8859-4); 39-41 Latvian (same three); 42-45 Portuguese (iso-8859-1, iso-8859-9, iso-8859-15, windows-1252); 46 Maltese iso-8859-3; 47-50 Czech (windows-1250, iso-8859-2, x-mac-ce, ibm852); 51-54 Slovak (same four); 55-60 Polish (windows-1250, iso-8859-2, iso-8859-13, iso-8859-16, x-mac-ce, ibm852); 61-66 Finnish (iso-8859-1, -4, -9, -13, -15, windows-1252); 67-71 Italian (iso-8859-1, -3, -9, -15, windows-1252); 72-77 Croatian (windows-1250, iso-8859-2, -13, -16, x-mac-ce, ibm852); 78-82 Estonian (windows-1252, windows-1257, iso-8859-4, -13, -15); 83-86 Irish (iso-8859-1, -9, -15, windows-1252); 87-90 Romanian (windows-1250, iso-8859-2, -16, ibm852); 91-95 Slovene (windows-1250, iso-8859-2, -16, x-mac-ce, ibm852); 96-100 Swedish (iso-8859-1, -4, -9, -15, windows-1252). A chunk is first filtered (R13a below); an empty result leaves everything unchanged. The filtered buffer is given to each active member in order; "found" ends the group (best member = that one, name = the member's name, with the Hebrew rule of R15); "not me" deactivates the member and, when none is active, the group is "not me". Confidence and best member: as in R9 (0.99 found, 0.01 not me, else the highest active member, strictly greater replaces, first of equal wins). R13a, the filter: scan the chunk keeping a segment start and a flag "saw a high byte"; a byte with the high bit set sets the flag; a byte that is an ASCII non-letter (below `A`, between `Z` and `a`, or above `z`; control characters, digits and punctuation included) ends the segment: when the flag is set and the segment (the bytes since the last start, separator excluded) is non-empty, the segment is output followed by one space byte and the flag is cleared; in any case the next segment starts after the separator. At the end a pending segment is output (no trailing space) when the flag is set. So only letter-and-high-byte runs that contain at least one high byte survive, separated by single spaces.
- **bitmap.charset.R14** [untestable: internal algorithm] Single-byte member (a language table plus one code page). Per byte `b` of the filtered buffer, `o = order[b]` from the code page's map (`order`: 255 illegal, 254 control, 253 symbol, 252 line break, 251 digit, otherwise the rank of the letter in the language, 0 the most frequent). `o` below 250 counts a character (`totalChar`); 255 makes the member "not me" and stops reading this buffer (the rest of the buffer is not examined and the previous-letter memory is not updated); 254 counts a control character. If `o < freqCharCount` of the language the frequent count rises, and when the previous byte's order (also memorised for symbols and controls, initially 255) was below `freqCharCount` too, a sequence is counted: the pair category (0..3) is the digit at `matrix[prev * freqCharCount + o]` (read `matrix[o * freqCharCount + prev]` instead for the "visual" Hebrew member) and that category's counter rises and `totalSeqs` rises. After each buffer, if detecting and `totalSeqs > 1024`: confidence above 0.95 makes "found", below 0.05 "not me". Confidence, with `typical` the language's `typicalPositiveRatio`: with no sequences 0.01; else `r = (cat3 / totalSeqs) / typical`, then `r = (r * (cat3 + cat2/4)) / totalChar`, then `r = (r * (totalChar - ctrl)) / totalChar`, then `r = (r * frequent) / totalChar`; if `r >= 1` it is 0.99. (Each step rounded to single precision; `cat2/4` is a float division.) The member's name is the code page's name, except for the Hebrew members (R15).
- **bitmap.charset.R15** [untestable: internal algorithm] Hebrew helper (member 10). It never answers by itself (its confidence is 0.0, it reports "detecting" forever and only "not me" when both Hebrew members 11 and 12 are "not me"). It reads the filtered buffer with memory `prev`, `beforePrev` (both a space at the start, kept across buffers) and two scores: on a space byte, if `beforePrev` is not a space (the word has more than one letter): `prev` is a final letter (EA, ED, EF, F3, F5: final kaf, mem, nun, pe, tsadi) adds 1 to the logical score, else `prev` a normal letter (EB, EE, F0, F4) adds 1 to the visual score; on a non-space byte, if `beforePrev` is a space and `prev` is a final letter, the visual score rises by one. Then `beforePrev = prev`, `prev = byte`. The name asked of members 11 and 12 (when one of them is the best or the "found" one) is decided here: let `d = logical - visual`; `d >= 5` gives `windows-1255`; `d <= -5` gives `iso-8859-8`; otherwise `m = confidence(member 11) - confidence(member 12)` (single precision): `m > 0.01` gives `windows-1255`, `m < -0.01` gives `iso-8859-8`; otherwise `d < 0` gives `iso-8859-8` and anything else `windows-1255`. (Observed: the Hebrew samples of the corpus, in windows-1255 and in iso-8859-8, both answer `windows-1255`.)
- **bitmap.charset.R16** [untestable: internal algorithm] Latin-1 prober (answers `windows-1252`). Its filter is different from R13a: scan the chunk keeping a segment start and a flag "inside a tag"; for each byte first update the flag (`>` clears it; otherwise `<` sets it), then, if the byte is an ASCII non-letter (as in R13a): when the segment before it is non-empty and the flag is clear, output the segment followed by one space byte; start the next segment after the byte. At the end, if the flag is clear, output the pending segment (no space). Each output byte `b` has a class: `0x41-0x5A` capital letter (ASC), `0x61-0x7A` small letter (ASS); `0x80-0xBF`: `83, 9A, 9C, 9E` are small accented others (ASO), `8A, 8C, 8E, 9F` capital accented others (ACO), `81, 8D, 8F, 90, 9D` undefined (UDF), the rest other (OTH); `C0-C5, C8-CF, D2-D6, D8-DC` capital accented vowel (ACV), `C6, C7, D0, D1, DD-DF` ACO, `D7` OTH; `E0-E5, E8-EF, F2-F6, F8-FC` small accented vowel (ASV), `E6, E7, F0, F1, FD-FF` ASO, `F7` OTH; every other byte below 0x80 and the bytes `A0-BF` are OTH. The class of the previous byte starts as OTH. The likelihood of the class pair (previous, current) is 0 (illegal), 1 (very unlikely), 2 or 3 (very likely) by this table: rows are the previous class UDF, OTH, ASC, ASS, ACV, ACO, ASV, ASO, columns the current class in the same order — UDF: 0 0 0 0 0 0 0 0; OTH: 0 3 3 3 3 3 3 3; ASC: 0 3 3 3 3 3 3 3; ASS: 0 3 3 3 1 1 3 3; ACV: 0 3 3 3 1 2 1 2; ACO: 0 3 3 3 3 3 3 3; ASV: 0 3 1 3 1 1 1 3; ASO: 0 3 1 3 1 1 3 3. A 0 makes the prober "not me" for good (its confidence is 0.01 from then on) and stops reading that buffer; otherwise counter[likelihood] rises. Confidence: 0.01 if "not me"; else with `total` the sum of the four counters: 0.0 when `total` is 0, otherwise `c = counter3 / total - counter1 * 20 / total`; a negative `c` gives 0.0, otherwise `c * 0.5`. Never above 0.5 (so any single-byte member with a higher confidence wins over it, and a perfect Latin-1 text is capped at 0.5).
- **bitmap.charset.R17** [untestable: internal algorithm] Escape prober (state "escape" of R3). Four machines in the order `hz-gb-2312`, `iso-2022-cn`, `iso-2022-jp`, `iso-2022-kr` (R7), fed the raw chunk bytes one by one: for each byte, every still-active machine is fed starting from the last active one down to the first; a machine in "error" is dropped (swapped with the last active, the active count falls); when none is left the prober is "not me"; a machine in "its me" ends the detection with its name. No answer by the end of the file gives `ascii` (R5). A later high byte discards the escape prober and starts the R4 probers (R3).
- **bitmap.charset.R18** [untestable: data format] Data files. `charset-statemachines.json`: `{"machines": {"<name>": {"classFactor": n, "cls": [256 ints], "states": [ints], "charLen": [ints]}}}` (R7), for `utf-8`, `shift-jis`, `euc-jp`, `gb18030`, `euc-kr`, `cp949`, `big5`, `euc-tw`, `hz-gb-2312`, `iso-2022-cn`, `iso-2022-jp`, `iso-2022-kr`. `charset-cjk.json`: `{"distribution": {"<table>": {"tableLength", "typicalDistributionRatio", "frequentOrders": [ranks below 512, as orders]}}, "jpContext": [83 rows of 83 ints]}` (R10, R11). `charset-sbcs.json`: `{"languages": {"<Lang>": {"freqCharCount", "typicalPositiveRatio", "matrix": "<freqCharCount^2 digits 0..3>"}}, "probers": [{"i", "lang", "name", "order": [256 ints], "reversed"?, "nameProber"?} | {"i", "kind": "hebrew"}]}` (R13, R14). The tables are the published models of the statistical detector the reference depends on (2.7 release; the single-byte language models come from the uchardet project, the frequency tables of the CJK encodings from the original Mozilla detector). To regenerate: read each language's sequence matrix and each code page's 256-entry order map from that release, keep the prober order of R13, and for the CJK tables keep the orders whose ranking value is below 512; nothing else of the tables is used by the algorithm.
- **bitmap.charset.R19** [untestable: internal algorithm] Short samples and what R1-R17 imply for them (all consequences, no extra rules): (a) a subtitle file is mostly ASCII, so the filters keep only the few words that contain a high byte, and a 40-byte file gives a prober at most a handful of letters; (b) a language table has no information about letters rarer than its rank limit (`freqCharCount`, 29..64), so a letter outside the limit lowers `frequent / totalChar` only; (c) with 0 sequences a member scores 0.01, and the Latin-1 prober (0.5 at best) then answers `windows-1252`; (d) a single-byte member that finds a few pairs of frequent letters, all of category 3, scores in the 0.3-0.8 range (the product of R14 shrinks only with the share of non-letters and non-frequent letters), above Latin-1's 0.5 cap when almost all of the characters are frequent, which is why one accented word is read as Hungarian, Slovak, Romanian or Greek rather than as the French/Spanish text it may be; (e) ties between code pages of one language (same order map on the bytes seen) are resolved by member order, so `iso-8859-2` wins over `windows-1250` for Hungarian bytes in the common range (member 21 before 22), `windows-1250` wins over `iso-8859-2` and `ibm852` for Slovak (member 51 first), and `iso-8859-7` wins over `windows-1253` (member 6 first).
- **bitmap.charset.R20** [untestable: worked examples, all recomputed with R1-R17 and equal to the recorded reference answers; `TestDetectCharsetCorpus` runs the whole corpus] The samples are SubRip files of 38-52 bytes; only the filtered words matter.
